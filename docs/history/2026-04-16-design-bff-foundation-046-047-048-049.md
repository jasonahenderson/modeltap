# 2026-04-16 — Design: BFF Foundation Bundle (WU-046 + WU-047 + WU-048 + WU-049)

## Scope

This is a bundled design covering four related WUs that form the BFF server foundation in `internal/bff/`:

- **WU-046** — JSON-RPC transport layer (`transport.go`): NDJSON reader/writer over `net.Conn`, message dispatch by method, request/response correlation, error formatting.
- **WU-047** — Protocol endpoint (`server.go`): Unix socket and TLS listeners, accept loop, graceful shutdown, `modeltap serve` integration.
- **WU-048** — Connection lifecycle state machine (`connection.go`): 9 states, transitions, heartbeat, health checks, timeout/grace-period logic.
- **WU-049** — Capability registration (`capabilities.go`): tool catalog, protocol version negotiation, project context capture, `MaxFrameSize`/attachment-size advertisement.

**Out of scope:** Session management (WU-050), conversation state (WU-051), streaming relay (WU-053), prompt engine (WU-054), model routing (WU-057–060), diagnostics taxonomy implementation details (WU-063, though diagnostic codes are referenced here for connection errors).

## Bundle Rationale

These four WUs share a single Go package (`internal/bff/`), a single goroutine model (per-connection), and deeply interleaved control flow: the transport (046) reads frames that the connection state machine (048) gates, the server (047) accepts connections and hands them to the state machine, and capability registration (049) is the first application-level exchange after the transport connects. Designing them separately would force each to make assumptions about the others' internal APIs.

## Design Decisions

### D1. Package structure

All four WUs produce files in `internal/bff/`. No sub-packages at this layer.

```
internal/bff/
  transport.go      — WU-046: FrameTransport, Dispatcher, error formatting
  transport_test.go
  server.go         — WU-047: Server, listener management, graceful shutdown
  server_test.go
  connection.go     — WU-048: Connection, state machine, heartbeat
  connection_test.go
  capabilities.go   — WU-049: CapabilityManager, version negotiation, project context
  capabilities_test.go
```

### D2. Transport layer (WU-046)

#### D2.1. FrameTransport

Wraps a `net.Conn` with the protocol's `FrameReader`/`FrameWriter` and adds JSON-RPC message-level semantics.

```go
// FrameTransport provides JSON-RPC 2.0 message exchange over a net.Conn.
// It is not safe for concurrent writes; the Connection serializes outbound messages.
// Concurrent reads are not expected (single read goroutine per connection).
type FrameTransport struct {
    conn   net.Conn
    reader *protocol.FrameReader
    writer *protocol.FrameWriter
    mu     sync.Mutex // guards writes only
}

func NewFrameTransport(conn net.Conn) *FrameTransport

// ReadMessage reads one NDJSON frame and decodes the JSON-RPC envelope.
// Returns the raw frame bytes alongside the decoded envelope for dispatch.
// On protocol.ErrFrameTooLarge, returns a TransportError with close=true.
func (t *FrameTransport) ReadMessage() (*Envelope, error)

// SendResponse writes a JSON-RPC 2.0 Response to the connection.
func (t *FrameTransport) SendResponse(resp *protocol.Response) error

// SendNotification writes a JSON-RPC 2.0 Notification to the connection.
func (t *FrameTransport) SendNotification(notif *protocol.Notification) error

// SendError writes a JSON-RPC 2.0 error response for the given request ID.
func (t *FrameTransport) SendError(id json.RawMessage, code int, message string, data any) error

// Close closes the underlying connection.
func (t *FrameTransport) Close() error
```

#### D2.2. Envelope — decoded message classification

```go
// Envelope is the result of decoding a single NDJSON frame.
// Exactly one of Request, Response, or Notification is non-nil.
type Envelope struct {
    Request      *protocol.Request
    Response     *protocol.Response
    Notification *protocol.Notification
    Raw          json.RawMessage // original frame bytes for logging/capture
}
```

The transport classifies frames by presence of fields:
- Has `method` + `id` → Request
- Has `id` + (`result` or `error`) → Response
- Has `method` + no `id` → Notification
- Otherwise → parse error (invalid JSON-RPC)

#### D2.3. Dispatcher — method routing

```go
// Handler processes a single JSON-RPC request and returns a result payload
// (marshalled into Response.Result) or an error.
type Handler func(ctx context.Context, conn *Connection, params json.RawMessage) (any, error)

// Dispatcher routes JSON-RPC requests to registered handlers by method name.
type Dispatcher struct {
    handlers map[string]Handler
}

func NewDispatcher() *Dispatcher

// Register adds a handler for a method. Panics on duplicate registration.
func (d *Dispatcher) Register(method string, h Handler)

// Dispatch routes a request to its handler. Returns MethodNotFound error
// if no handler is registered.
func (d *Dispatcher) Dispatch(ctx context.Context, conn *Connection, req *protocol.Request) (any, error)
```

#### D2.4. JSON-RPC error codes

Per JSON-RPC 2.0 spec, plus application-level codes:

```go
const (
    // Standard JSON-RPC 2.0 error codes
    CodeParseError     = -32700
    CodeInvalidRequest = -32600
    CodeMethodNotFound = -32601
    CodeInvalidParams  = -32602
    CodeInternalError  = -32603

    // Application-level error codes (server-defined range: -32000 to -32099)
    CodeNotReady           = -32000 // request received before connection is in 'ready' state
    CodeSessionLocked      = -32001 // session locked by another harness
    CodeVersionMismatch    = -32002 // protocol version incompatible (terminal)
    CodeCapabilityError    = -32003 // capability registration/update failed
    CodeProviderError      = -32004 // upstream provider returned an error
    CodeSessionNotFound    = -32005 // session ID not found
    CodeTurnNotFound       = -32006 // turn ID not found
    CodeModelUnavailable   = -32007 // requested model not in registry
)
```

#### D2.5. Transport validation (inherited from WU-039 review)

The transport layer validates at the message edge before dispatch:

1. **`turn.submit` sequence presence**: Use `json.Decoder` with strict field checking. If `sequence` is absent from the raw JSON (not just zero), reject with `CodeInvalidParams` and message `"turn.submit requires sequence field"`.

2. **`turn.submit` mode validation**: After decoding `TurnSubmit`, call `mode.Valid()`. If invalid, reject with `CodeInvalidParams` and message `"invalid mode: <value>"`.

3. **Oversize frame handling**: On `protocol.ErrFrameTooLarge` from `FrameReader.ReadFrame`, the transport MUST close the connection immediately. The reader is left mid-frame and cannot be safely resynchronized. Before closing, send an error response if possible (best-effort; the connection may already be in a bad state).

```go
// ValidateTurnSubmit performs edge validation on a turn.submit request.
// Called by the transport before dispatching to the session handler.
func ValidateTurnSubmit(raw json.RawMessage) (*protocol.TurnSubmit, error)
```

Implementation: unmarshal into `TurnSubmit`, then re-scan `raw` for `"sequence"` key presence using `json.NewDecoder` walking tokens (or a simpler byte scan for `"sequence":`). This avoids a custom struct with `*int` for a single validation check.

#### D2.6. Request/response correlation

The transport does not manage correlation itself — it's stateless per frame. Correlation is the responsibility of the `Connection` (WU-048), which tracks in-flight requests by their `id` when the server needs to send streaming events tagged with a `turn_id`.

### D3. Server (WU-047)

#### D3.1. Server struct

```go
// Server manages BFF protocol listeners and accepts connections.
type Server struct {
    store      storage.Store
    dispatcher *Dispatcher
    config     ServerConfig
    
    // listener management
    listeners []net.Listener
    
    // connection tracking
    mu    sync.Mutex
    conns map[*Connection]struct{}
    
    // lifecycle
    ctx    context.Context
    cancel context.CancelFunc
    wg     sync.WaitGroup
}

type ServerConfig struct {
    // Unix socket path (solo/local profile)
    SocketPath string // default: ~/.local/share/modeltap/server.sock
    
    // TLS config (team/enterprise profile)
    TLSAddress  string // e.g., ":9443"
    TLSCertFile string
    TLSKeyFile  string
    
    // Socket permissions
    SocketMode os.FileMode // default: 0600
    
    // Connection limits
    MaxConnections int // default: 100
    
    // Timeouts (exposed for testing)
    HeartbeatInterval time.Duration // default: 15s
    HeartbeatTimeout  time.Duration // default: 30s
    GracePeriod       time.Duration // default: 10s
}

func NewServer(store storage.Store, config ServerConfig) *Server

// Start begins listening on configured endpoints.
// Returns after listeners are bound (does not block for connections).
func (s *Server) Start() error

// Shutdown gracefully stops the server. Closes listeners, then waits
// for active connections to drain (up to timeout).
func (s *Server) Shutdown(ctx context.Context) error
```

#### D3.2. Listener management

```go
// startSocketListener creates a Unix domain socket listener.
// Removes stale socket file if it exists and no process is listening.
func (s *Server) startSocketListener() (net.Listener, error)

// startTLSListener creates a TLS listener on the configured address.
func (s *Server) startTLSListener() (net.Listener, error)

// acceptLoop runs the accept loop for a single listener.
// Each accepted connection is handed to handleConnection in a new goroutine.
func (s *Server) acceptLoop(ln net.Listener)
```

Stale socket detection: attempt `net.Dial("unix", path)`. If dial succeeds, another server is running — return error. If dial fails with connection refused or timeout, the socket is stale — remove and rebind.

Socket file permissions: after `net.Listen("unix", path)`, call `os.Chmod(path, config.SocketMode)`. Default `0600` (owner-only). Group-writable (`0660`) only when explicitly configured.

#### D3.3. Connection acceptance

```go
// handleConnection wraps the accepted net.Conn in a Connection,
// runs the connection lifecycle, and cleans up on exit.
func (s *Server) handleConnection(conn net.Conn)
```

Flow:
1. Check `MaxConnections` — reject if at limit (close with no response)
2. Create `FrameTransport` from `net.Conn`
3. Create `Connection` with initial state `connecting`
4. Register connection in `s.conns`
5. Run `conn.Run()` (blocking — runs read loop)
6. On return: deregister, clean up locks, close transport

#### D3.4. Integration with `modeltap serve`

The existing `modeltap serve` command (in `internal/cli/`) starts the reverse proxy. WU-047 extends it to also start the BFF server:

```go
// In serve command's Run function:
bffServer := bff.NewServer(store, bff.ServerConfig{...})
if err := bffServer.Start(); err != nil {
    return fmt.Errorf("BFF server start: %w", err)
}
defer bffServer.Shutdown(ctx)
```

Both the proxy and BFF share the same `storage.Store` instance. The BFF does not proxy HTTP — it has its own protocol over socket/TLS.

### D4. Connection lifecycle state machine (WU-048)

#### D4.1. States and transitions

```go
type ConnState int

const (
    // ConnDiscovering is the initial harness-side state (not used server-side).
    // The server creates connections in ConnConnecting.
    ConnDiscovering ConnState = iota
    
    // ConnStarting is the harness-side state for auto-starting the server.
    // Not used server-side.
    ConnStarting
    
    // ConnConnecting: TCP/socket connection established, no protocol exchange yet.
    ConnConnecting
    
    // ConnAuthenticating: TLS handshake complete, OIDC/auth in progress.
    // For Unix socket connections, this state is skipped.
    ConnAuthenticating
    
    // ConnRegistering: capabilities.register received, being processed.
    ConnRegistering
    
    // ConnReady: fully operational. Requests accepted.
    ConnReady
    
    // ConnDegraded: operational but a dependency is unhealthy.
    // Requests still accepted. Connection continues heartbeat.
    ConnDegraded
    
    // ConnReconnecting: heartbeat lost. Not used server-side
    // (server sees the connection as gone). Harness-side only.
    ConnReconnecting
    
    // ConnFailed: terminal. Connection will be closed.
    ConnFailed
)

// String returns the canonical FEAT-0008 state name. These values are
// wire-visible (health responses, diagnostics, session sync) and MUST
// match FEAT-0008 §"Connection states" verbatim. Tests pin them.
func (s ConnState) String() string // "discovering", "starting", "connecting", etc.
```

Server-side states: `ConnConnecting` → `ConnAuthenticating` (TLS only) → `ConnRegistering` → `ConnReady` ⇄ `ConnDegraded` → `ConnFailed`.

**Wire visibility note (resolves B-05):** `ConnState.String()` output reaches the wire via `HealthResponse`, `Diagnostic`, and `session.sync` payloads. The `String()` implementation must return the exact FEAT-0008 names. A test (`TestConnState_StringValues`) pins every constant to its FEAT-0008 name. Future: consider moving the state string constants to `internal/protocol/` for a single source of truth shared with the harness (Track B).

States `ConnDiscovering`, `ConnStarting`, and `ConnReconnecting` are harness-side only (Track B). The server never enters them.

#### D4.2. Connection struct

```go
// Connection represents a single harness-to-server protocol session.
// One goroutine reads (readLoop), one goroutine writes (serialized by transport.mu).
// The Connection gates method dispatch based on state.
type Connection struct {
    id        string // unique connection ID (UUID)
    transport *FrameTransport
    server    *Server
    
    // State machine
    mu    sync.RWMutex
    state ConnState
    
    // Heartbeat monitoring (server is passive — harness initiates pings)
    lastPing     time.Time // updated when harness sends connection.ping
    heartbeatCtx context.Context
    heartbeatCancel context.CancelFunc
    
    // Capabilities (populated during registration)
    capabilities *CapabilityManager
    
    // Session binding (set when a session is active on this connection)
    sessionID string
    
    // Lifecycle
    ctx    context.Context
    cancel context.CancelFunc
    done   chan struct{}
}

func NewConnection(id string, transport *FrameTransport, server *Server) *Connection
```

#### D4.3. State transition rules

```go
// validTransitions defines the allowed state machine transitions.
// The server enforces these; any attempt to transition outside this
// map is a bug (panic in debug, log+ignore in release).
var validTransitions = map[ConnState][]ConnState{
    ConnConnecting:     {ConnAuthenticating, ConnRegistering, ConnFailed},
    ConnAuthenticating: {ConnRegistering, ConnFailed},
    ConnRegistering:    {ConnReady, ConnFailed},
    ConnReady:          {ConnDegraded, ConnFailed},
    ConnDegraded:       {ConnReady, ConnFailed},
}

// transition atomically changes state. Returns false if the transition
// is not valid. On valid transition, fires state-change callbacks.
func (c *Connection) transition(to ConnState) bool
```

#### D4.4. Read loop and dispatch gating

```go
// Run starts the connection's read loop and heartbeat monitor.
// Blocks until the connection is closed or fails.
func (c *Connection) Run()
```

The read loop:
1. Read frame via `transport.ReadMessage()`
2. On `ErrFrameTooLarge`: close connection immediately (per SR-039-01)
3. Classify envelope (Request / Notification / Response)
4. **Gate check**: if state is not `ConnReady` or `ConnDegraded`, only allow:
   - `capabilities.register` (in `ConnRegistering`)
   - `connection.ping` (in any state after `ConnConnecting`)
   - All other methods → reject with `CodeNotReady`
5. Dispatch via `server.dispatcher.Dispatch()`
6. Send response or error

**Reconnection note (A-05):** after a harness reconnects and completes `capabilities.register`, the first method it sends in `ConnReady` state is typically `session.sync` (FEAT-0008 §"Reconnection flow"). This is handled by the standard `ConnReady`/`ConnDegraded` gate — no special case needed. The `session.sync` handler (WU-064) returns active turn status, pending tools, and branch states.

#### D4.5. Heartbeat (resolves B-01, B-03)

Per FEAT-0008 §"Heartbeat": the **harness** sends `connection.ping` every 15s; the **server** replies with `connection.pong`. The server is passive — it does not initiate pings. It monitors receipt of harness pings and transitions to `ConnFailed` when they stop arriving.

```go
// startHeartbeatMonitor runs a goroutine that checks for harness ping timeout.
// The server does NOT send pings — it only monitors receipt of harness-initiated
// connection.ping requests. Started when connection reaches ConnReady.
func (c *Connection) startHeartbeatMonitor()
```

Heartbeat monitor (runs alongside the read loop):
- Check every `HeartbeatInterval` (15s): if `time.Since(lastPing) > HeartbeatTimeout` (30s), transition to `ConnFailed` and close
- `lastPing` is initialized to `time.Now()` at connection creation (A-01 fix: ensures the timeout clock doesn't start before the harness has a chance to register)

The `connection.ping` request handler updates `lastPing` and returns an empty pong:

```go
func handleConnectionPing(ctx context.Context, conn *Connection, params json.RawMessage) (any, error) {
    conn.mu.Lock()
    conn.lastPing = time.Now()
    conn.mu.Unlock()
    return &protocol.ConnectionPong{}, nil // ConnectionPong has no fields per protocol-types design
}
```

`ServerConfig.HeartbeatInterval` is retained for configuring the monitor's check frequency. It is NOT the harness's ping interval (that is a harness-side setting in WU-074).

#### D4.6. Health and ready handlers

```go
func handleConnectionHealth(ctx context.Context, conn *Connection, params json.RawMessage) (any, error)
```

Returns a `protocol.HealthResponse` (from WU-041 `health.go`) with all fields populated (resolves A-03):
- `server_version`: from build-time constant
- `protocol_version`: from `protocol.ProtocolVersion`
- `uptime_seconds`: computed from server start time
- `auth`: `DependencyStatus{Status: "ready"}` (stub until auth WU lands)
- `storage`: health from `store.Ping()` — `"ready"` or `"unavailable"` with reason
- `capabilities`: `DependencyStatus{Status: "ready", Method: "register"}` if registered, `"unavailable"` otherwise
- `providers`: per-provider health from registry (stub `map[string]ProviderStatus{}` until WU-057 lands)
- `routing`: `DependencyStatus{Status: "ready"}` (stub until WU-059 lands)
- `active_session`: populated from `conn.sessionID` if bound, nil otherwise

```go
func handleConnectionReady(ctx context.Context, conn *Connection, params json.RawMessage) (any, error)
```

Returns `ReadyResponse{Ready: ...}` where Ready is true only when (resolves A-02):
- `conn.State() == ConnReady`
- `store.Ping()` succeeds (storage is healthy)
- At least one provider is healthy (when WU-057 lands; initially true as stub)

Per FEAT-0008 line 445: "returns true only if auth, storage, capability registration, and at least one routing target are healthy."

#### D4.7. Grace period and session lock release

When a connection transitions to `ConnFailed`:
1. If `conn.sessionID != ""`, schedule lock release after `GracePeriod` (10s):
   - Start a goroutine that waits `GracePeriod`
   - If no new connection resumes the session within that window, call `store.ReleaseSessionLock(sessionID, conn.id)`
   - If a new connection claims the session (via `session.resume`), cancel the grace timer
2. Total time from last pong to lock release: `HeartbeatTimeout + GracePeriod` = 40s

```go
// scheduleGracePeriodRelease starts a timer to release the session lock
// after the grace period expires. Returns a cancel function that prevents
// the release (used when a reconnecting harness resumes the session).
func (c *Connection) scheduleGracePeriodRelease() context.CancelFunc
```

### D5. Capability registration (WU-049)

#### D5.1. CapabilityManager

```go
// CapabilityManager tracks tools, protocol version, and project context
// for a single connection.
type CapabilityManager struct {
    mu sync.RWMutex
    
    // Protocol
    negotiatedVersion string
    
    // Tools
    tools map[string]protocol.ToolDefinition // keyed by "namespace:name"
    
    // Project context
    project protocol.ProjectContext
    
    // Limits advertised in handshake
    maxFrameSize     int
    maxAttachmentSize int
}

func NewCapabilityManager() *CapabilityManager
```

#### D5.2. Registration handler

```go
func handleCapabilitiesRegister(ctx context.Context, conn *Connection, params json.RawMessage) (any, error)
```

Flow:
1. Decode `CapabilitiesRegister` from params
2. **Version negotiation**: check `ProtocolVersion` against server's supported range
   - Currently server supports exactly `"1"` (single version)
   - If client version != `"1"` → respond with `CodeVersionMismatch`, transition to `ConnFailed`
   - Future: server declares `[min, max]` range, selects highest mutually supported
3. **Tool catalog validation**: for each tool in `Tools`:
   - Validate required fields: `name`, `description`, `input_schema`
   - Validate `input_schema` is valid JSON
   - Validate `risk_level` is one of: `"read_only"`, `"write"`, `"execute"`, `"destructive"`
   - Validate `output_envelope` is one of: `"text"`, `"json"`, `"binary"`, `"image"`
   - On any validation failure: reject entire registration with `CodeCapabilityError`
4. **Project context**: store `project.Root`, `project.ConfigFile`, `project.ConfigContent`
5. **Transition**: `ConnRegistering` → `ConnReady`
6. **Response**: return `protocol.CapabilitiesRegisterResponse` (defined in protocol-types design WU-041 `tools.go`)

**(Resolves B-02):** The response type is `protocol.CapabilitiesRegisterResponse`, NOT a local BFF type. The protocol-types design defines it with fields `{registered []ToolDefinition, server_capabilities ServerCapabilities, rejected []RejectedTool}`. The handler populates:
- `Registered`: the validated tool catalog (tools that passed validation)
- `Rejected`: tools that failed validation, with reason strings
- `ServerCapabilities`: populated with `protocol_version`, `max_frame_size`, and `max_attachment_size`

**Protocol-types amendment needed (cross-bundle):** `ServerCapabilities` (WU-041 `health.go`) must be amended to include `max_frame_size int` and `max_attachment_size int` fields per WU-039 review finding A-05. The existing fields (`protocol_version`, `protocol_version_range`, `supported_transforms`) are retained. This amendment is recorded here and must be applied to the protocol-types design doc before Phase 3.

Note: tool validation failures no longer reject the entire registration (as originally designed). Instead, valid tools are registered and invalid tools appear in the `rejected` array. The handler returns success with partial registration. This matches the protocol-types design's `RejectedTool` type.

#### D5.3. Capability update handler

```go
func handleCapabilitiesUpdate(ctx context.Context, conn *Connection, params json.RawMessage) (any, error)
```

Processes `CapabilitiesUpdate` (from WU-039 `messages.go`):
- `AddedTools`: validate and add to catalog
- `RemovedTools`: remove by name (namespace:name key)
- If any added tool fails validation, reject entire update (atomic)

Response: `CapabilitiesUpdateResponse{Accepted: true}`.

#### D5.4. Replay prevention

`capabilities.register` can only be called once per connection (in `ConnRegistering` state). After successful registration, the connection transitions to `ConnReady`. Any subsequent `capabilities.register` is rejected with `CodeNotReady` because the connection is no longer in `ConnRegistering`.

This is enforced by the dispatch gate (D4.4), not by separate logic.

#### D5.5. Capabilities re-request (resolves B-04)

The server can proactively ask the harness to re-register capabilities via the `capabilities.request` notification (defined in protocol-types WU-040 as `CapabilitiesRequestEvent`).

```go
// RequestReregistration sends a capabilities.request notification to the harness,
// asking it to re-send capabilities.register. Used on reconnection (when the
// harness's tool catalog may have changed) or when the server detects tool
// schema drift.
func (cm *CapabilityManager) RequestReregistration(conn *Connection, reason string) error
```

Implementation: send `protocol.Notification{Method: "capabilities.request", Params: marshal(CapabilitiesRequestEvent{Reason: reason})}` via `conn.transport.SendNotification()`.

Known reason values (per FEAT-0008 line 208): `"reconnection"`, `"tool_schema_drift"`.

Wiring points:
- **Reconnection flow** (WU-050 `session.resume`): if the resuming connection's tool catalog differs from the session's last-known catalog, the session handler sends `capabilities.request` with reason `"reconnection"`.
- **Diagnostics** (WU-063): `MT-CONN-010` (capability_registration_failed) may trigger a re-request after the harness corrects the issue.

The harness responds by calling `capabilities.register` again (handled by D5.2). The server replaces the old catalog atomically.

#### D5.6. Project context refresh

Project context is refreshed on every `session.resume` (WU-050) — the harness sends updated `config_content` so edits to project config take effect immediately. The `CapabilityManager` exposes:

```go
// UpdateProjectContext replaces the stored project context.
// Called on session.resume with the harness's current config snapshot.
func (cm *CapabilityManager) UpdateProjectContext(pc protocol.ProjectContext)

// ProjectContext returns the current project context.
func (cm *CapabilityManager) ProjectContext() protocol.ProjectContext

// Tools returns a snapshot of the current tool catalog.
func (cm *CapabilityManager) Tools() []protocol.ToolDefinition

// NegotiatedVersion returns the protocol version selected during registration.
func (cm *CapabilityManager) NegotiatedVersion() string
```

#### D5.6. MaxFrameSize and attachment-size advertisement (from WU-039 review A-05)

The `CapabilitiesRegisterResponse` includes `max_frame_size` (currently `protocol.MaxFrameSize` = 10 MiB) and `max_attachment_size` (configurable, default 5 MiB). The harness uses these to refuse oversize attachments before serializing.

If a harness sends an attachment exceeding `max_attachment_size`, the server rejects the `turn.submit` with a diagnostic referencing `MT-CONN-013` (attachment too large). This diagnostic code is defined in WU-041's `errors.go` per review finding A-05.
