# v0.3.0 Implementation Review

**Reviewer:** Claude Opus 4.7 (1M context), with parallel exploration
subagents for storage, protocol, BFF, and harness audits, then a second
parallel pass framed as adversarial QA and SRE perspectives.
**Date:** 2026-05-05
**Phase reviewed:** Phase 3 — Implementation
**Scope:** Independent implementation review of `release/v0.3.0` against
the accepted v0.3.0 designs, ADR-0015, and FEAT-0015/0016/0017 foundation
scope. Complements (does not replace) `v0.3.0-release-readiness.md`.

## Method

1. Audit pass — four parallel read-only subagents, one per design bundle:
   - WU-109 storage vs `2026-05-05-design-run-storage-109.md`
   - WU-110 protocol vs `2026-05-05-design-run-protocol-110.md`
   - WU-111/112/113 BFF runtime vs `2026-05-05-design-bff-run-runtime-111-113.md`
   - WU-114/115/116 harness surface vs `2026-05-05-design-harness-run-surface-114-116.md`
2. Adversarial pass — two parallel read-only subagents framed as senior QA
   and on-call SRE, given the audit-pass findings as context to avoid
   retreading and instructed to find what would break under real-world use.
3. Verification pass — every load-bearing claim was checked against the
   actual code before inclusion here. Claims that did not hold up are
   listed under "Discounted claims" so future reviewers do not re-discover
   them as defects.

`go build ./...`, `go vet ./...`, and `go test ./...` all pass clean on
`release/v0.3.0` at HEAD.

## Verdict

Ship-with-followups. The implementation is structurally complete, matches
the readiness review's high-level claim, preserves backward compatibility
with v0.2.x clients, and has no defect that is individually
release-blocking. However, the cumulative gaps below mean the system is
likely to produce silent failures and operator pain within the first
operational weeks unless several of them are addressed before tag.

## What is solid (verified)

- **Storage (WU-109).** Schema version 3 migration is atomic and tested
  for fresh + step-wise paths. All promised tables, indexes, and Store
  APIs are present, including `UNIQUE(turn_id)` on `run_turns`
  (`internal/storage/sqlite.go:344`) enforcing the FEAT-0015 one-turn /
  one-run invariant. Extension JSON slots reserved on checkpoints for
  context, artifacts, policy, workspace, memory, and routing.
- **Protocol (WU-110).** 100% conformance: all 13 `run.*` methods,
  16 run events, and 9 stages match the design. Backward compatibility
  preserved cleanly — `TurnSubmitResponse.RunID` and the new `run_id`
  on legacy `token.delta` / `turn.complete` are `omitempty`
  (`internal/protocol/messages.go:278`,
  `internal/protocol/events.go:38,102,130,145`).
- **Detached transcript invariant.** Implemented and tested.
  `internal/harnesshost/adapter.go:253-265` buffers run deltas when no
  run is attached or when the delta belongs to a different run;
  `adapter.go:204-223` replays on attach; covered by
  `TestAdapterBuffersDetachedRunDeltasUntilAttach` at
  `adapter_test.go:332-354`.
- **`AppendRunEvent` is properly transactional.**
  `internal/storage/runs.go:186-229` wraps the seq read, event insert,
  optional checkpoint insert, and run-state update in a single
  `BeginTx`. SQLite serializes write transactions, so two concurrent
  `AppendRunEvent` calls do not lose events.
- **`run.permissions` is wired end-to-end.** Handler registered at
  `internal/bff/run_runtime.go:27`, implemented at
  `internal/bff/run_controls.go:268`, tested at
  `internal/bff/run_controls_test.go:131`.

## Findings

### Critical (silent failures likely in production)

**C1. Relay errors are swallowed, leaving runs frozen with no signal.**
`internal/bff/turn.go:249` invokes the streaming relay as
`turn, _ := relay.Relay(...)`. If the provider stream errors after
`run.started` and the first `stage_changed` events have been appended,
no `EventRunFailed` is written, no log line is emitted with run/turn
context, and the run is left in `stage=model_call, status=running`
indefinitely. Combined with C2 below, a frozen run is invisible from
both the server and the client.

Recommended fix: capture the error from `relay.Relay`, append
`EventRunFailed` with reason details via `appendRunLifecycle`, and log
with `run_id`/`turn_id` context.

**C2. `run.heartbeat` is a stateless echo.**
`internal/bff/run_controls.go:314-323` reads the run and returns its
current status with no timestamp side-effect. A run can sit stale for
hours and heartbeat will keep returning `running`. Either delete the
method from the protocol surface or wire it to update a `heartbeat_at`
column that a stuck-detector reads.

**C3. `RunSummary.Stuck` and `StuckSeconds` are dead protocol.**
Defined in `internal/protocol/runs.go:126-127` and named in the design's
stuck-detection threshold (300 s), but `grep` finds zero assignments
across the codebase. Clients cannot detect stuck runs through the
documented surface.

**C4. `runRegistry` and `turnTracker` are unbounded in memory.**
`internal/bff/run_registry.go:8-26` and `internal/bff/turn.go:19-50`
hold maps with no TTL, no LRU, and no size cap. Cleanup relies on
defer-deregister inside the relay path; any panic, leaked goroutine, or
process-lifetime connection accumulates entries forever. Eviction on
terminal status (or a small TTL after terminal) would suffice for the
foundation release.

### High (correctness gaps and operational risk)

**H1. `turn.submit` pre-dispatch persistence is not transactional.**
`internal/bff/turn.go:144-166` makes four sequential storage calls
(`createRunRecord`, `AppendUserTurn`, `CreateTurn`, `LinkTurnToRun`)
without a surrounding transaction. The design's "one durable
pre-dispatch transaction" contract (design WU-111-113 §turn.submit Flow)
is not met. If `CreateTurn` or `LinkTurnToRun` fails after `CreateRun`
succeeds, the run is orphaned without its owning turn link.

**H2. Inactive stages never emitted.** The design promised that
`context_plan`, `validation`, and `artifact_capture` stages would be
emitted as no-ops with reason `not_enabled_v0.3.0` so v0.3.1+ have a
trace point to enable. Constants exist in `internal/storage/runs.go`
but no code emits them.

**H3. No retention/pruning for `run_events` (and friends).** Schema v3
adds `run_events`, `run_checkpoints`, `run_model_calls`,
`run_tool_results` but no expiry/prune logic. ADR-0005 mandates
retention-based pruning for capture data; the v0.3.0 schema does not
extend that policy to runs. At any meaningful run rate this becomes a
disk-full failure mode rather than a query-performance one.

**H4. Schema migration is one-way.** `internal/storage/upgrade_test.go`
confirms the downgrade guard rejects any DB whose `user_version`
exceeds the binary's `MaxKnownSchemaVersion`. Rolling back from v0.3.0
to v0.2.x leaves the DB at `user_version=3`; v0.2.x will refuse to
start until an operator manually resets it. At minimum a documented
rollback runbook is required; a downgrade migration would be safer.

**H5. No structured logging or metrics on the run path.** No
`run_id`/`turn_id`-tagged log records for lifecycle transitions or
errors; no counters for active/queued/cancelled; no histograms for
replay-gap rate or attach contention. The on-call SRE has no signal
short of querying SQLite directly.

**H6. TOCTOU window on attach lease.**
`internal/bff/run_controls.go:107-123` reads `run.AttachmentState` and
`run.AttachedConnectionID`, then appends the attach event. The check
and the write are not atomic; under simultaneous attach attempts both
callers can pass the conflict check before either writes. Likely
mitigated in practice by single-process serialization through the
registry mutex, but unverified by test and not enforced by a database
constraint.

### Medium (untested transitions and lesser gaps)

**M1. Untested state transitions** with code paths that allow them:
- `cancel` while `waiting_permission`: no current-status guard at
  `run_controls.go` cancel handler; appends a cancelled event regardless.
- `fork` of a `failed` run: no parent-status check at
  `run_controls.go:229`; child is queued.
- `cancel` racing with provider `EventRunCompleted`: both write terminal
  state without CAS; last writer wins.
- `resolve_permission` racing with `cancel`: resolve appends a
  non-terminal event after cancel marks terminal; orphaned event in
  the stream.

**M2. No idempotency test for duplicate `turn.submit` with same key.**
The flow at `internal/bff/turn.go:140-166` constructs an idempotency
key but does not verify behavior on retry-after-response-loss.

**M3. No end-to-end tests for the harness run commands.** `/run`,
`/attach`, `/detach`, `/cancel`, `/retry`, `/continue`, `/fork` are
wired in `internal/harnesshost/production_runtime.go:684-840` but have
zero dedicated test coverage in `production_runtime_test.go`.

**M4. Protocol JSON fixtures are thin.**
`internal/protocol/runs_test.go` covers ~3 of the ~16 cases the design's
"Tests" section enumerates (every method, non-monotonic seq rejection,
input_required/stuck logic, replay fidelity modes, permission
resolution).

**M5. No test for `LinkTurnToRun` UNIQUE(turn_id) enforcement.** The
schema constraint exists at `internal/storage/sqlite.go:344` but no
test exercises it.

**M6. `replayFidelity` is reported but not enforced in the harness.**
`internal/bff/run_controls.go` returns `summary` fidelity when events
are sparse, but `projectRunReplay`
(`internal/harnesshost/production_runtime.go:602-627`) does not branch
on the fidelity label — it replays whatever events arrive. A large gap
is reported as a status string only.

## Discounted claims (recorded so future reviewers do not re-find them)

- **"Concurrent `AppendRunEvent` loses events."** Incorrect.
  `internal/storage/runs.go:186-229` wraps read + insert + state update
  in a single `BeginTx`. SQLite serializes write transactions.
- **"Two runs can link the same turn."** Incorrect. The schema has
  `UNIQUE (turn_id)` on `run_turns` at
  `internal/storage/sqlite.go:344`, which is stricter than per-run
  uniqueness.
- **"v0.3.0 / v0.2.x protocol version mismatch breaks the handshake."**
  Incorrect. `ProtocolVersion = "1"` at
  `internal/protocol/protocol.go:56` is unchanged across these
  releases. The real cross-version concern is narrower: a v0.2.x server
  returns `MethodNotFound` for `run.*` calls.
- Quantitative growth estimates from the SRE pass (`10k runs/day → 1 GB
  heap @ 30 days`, `5 GB disk`) are illustrative orders-of-magnitude,
  not measured. The qualitative shape (unbounded → eventually
  OOM/disk-full) is what matters.

## Recommendations

In rough priority for what to land before a v0.3.0 tag:

1. Capture and persist the relay error in `internal/bff/turn.go:249` —
   append `EventRunFailed` with reason on non-nil error and log with
   `run_id` context. (C1)
2. Wrap the `turn.submit` four-call pre-dispatch sequence in a single
   transaction. (H1)
3. Decide `run.heartbeat`: delete or make it update a `heartbeat_at`
   column. Same call, populate `RunSummary.Stuck` /
   `StuckSeconds` so the protocol field is not dead. (C2 + C3)
4. Add eviction (TTL or size-bounded) to `runRegistry` and
   `turnTracker`, even if just on terminal state. (C4)
5. Add CAS or status-guard to terminal-state writes in `run.cancel` so
   it cannot race the provider's completion event into an inconsistent
   terminal status. (M1)

Items not landed before tag should be tracked as patches or v0.3.x WUs
rather than carried as informal followups.

## Limitations of this review

- Read-only static review. No load testing, no chaos testing, no
  multi-process integration testing.
- Quantitative load estimates from the SRE pass are not measured.
- Claims about goroutine and FD leak shapes are based on code reading,
  not on profiling.
- Backward-compat reasoning was checked at the protocol-shape level,
  not by running v0.2.x clients against a v0.3.0 server in a real
  harness.
