## Architectural decisions documented

The Phase 2 review processed before implementation surfaced
significant ambiguities in the Phase 1 design. v0.2.2 ships with all
of those resolved concretely:

- **Permission gating** — broker logic in `ProductionRuntime` (sync.Map
  of per-`ToolCallID` channels), `ToolDispatcher` unchanged.
- **WU-104 split** — three slices (104a/b/c) so WU-105 has a stable
  WU-104a foundation.
- **`InterruptRun`** — uses existing `Client.CancelTurn` (no new RPC);
  fallback synthesizes `RunStoppedEvent`.
- **`LoadPreview` path** — adapter `tokenAttachments` map.
- **`SubmitTurn` async/sync bridge** — turned out unnecessary; the
  existing `Client.SubmitTurn` is already synchronous. The Phase 1
  design's `SubmitTurnSync` promise hook was solving a problem that
  doesn't exist post-App-deletion.
- **`DispatchCommand` event-surfacing** — `ProductionRuntime` emits
  `HostStatusEvent` directly via the deferredSender; out-of-band.
- **`ViewportState` cache** — preallocated pointer in `New()`, but
  the deeper fix was making `Update.refresh()` apply `SetContent` to
  the persistent viewport (the cache trick was insufficient on its
  own).
- **Bare `modeltap`** — does NOT change to launch shell (Codex #6
  rejected); falls back to cobra default help.

## Explicit deferrals carried into v0.2.3+

- **`/compact`, `/history`, `/mcp` slash commands** — return "not yet
  wired" status events. Implementation requires the audit's refactor
  column to extract sync helpers from the deleted handlers.
- **MCP lazy-start** — `MCPManager` is not yet constructed in
  `NewProductionRuntime`. Real MCP integration is a v0.2.3
  enhancement.
- **`ApproveOnce` vs `ApproveSession`** — the executor's
  `permission.Approve(toolName)` call collapses both into "session"
  level. Distinguishing requires a small `framework.go` refactor.
- **`turn.cancel` BFF support** — `InterruptRun` synthesizes
  `RunStoppedEvent` on error so the UX is preserved, but if the
  deployed BFF doesn't implement `protocol.MethodTurnCancel` the
  underlying cancellation won't fire server-side. Verify before
  shipping to production users.

## Risks acknowledged at tag time

- **Production reach.** v0.2.2 ships the `modeltap shell` entrypoint
  but it has not been exercised against a deployed BFF in this
  release cycle (only against the internal `BFFStub`). End-to-end
  smoke testing against a real `modeltap start` server is recommended
  before announcing.
- **Branch.** Tagged on `spike/scrolling-surface-eval`. The branch
  retarget to a release branch is pending TPM decision; per
  `.agents/process.md` §"Tag update policy", an unpublished tag may
  be moved.
- **Test fixture coverage.** The BFF stub speaks four methods
  (`capabilities.register`, `turn.submit`, `turn.cancel`, `ping`).
  Realistic stream-event handling (StreamTokenMsg / StreamCompleteMsg
  emission) is exercised by the projection unit tests but not by
  end-to-end stub tests.
