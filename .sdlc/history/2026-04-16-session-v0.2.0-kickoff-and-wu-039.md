## 2. WU-039 — Protocol core messages and framing

Delivered per the agent-team workflow: designer → tester (red) → backend (green) → security reviewer.

### Design (designer role)

Log: `.sdlc/history/2026-04-16-design-wu-039-protocol-core.md`

Key decisions:
- Package layout: `internal/protocol/{protocol.go, messages.go, protocol_test.go}`. Later WUs add `events.go`, `tools.go`, etc.
- JSON-RPC 2.0 envelope types (`Request`, `Response`, `ErrorObject`) live in `protocol.go` with `json.RawMessage` for `Params`/`Result`/`ID`/`Data` so typed decoding is deferred to the handler layer.
- NDJSON framing: `FrameReader` / `FrameWriter` with `MaxFrameSize = 10 MiB`, dedicated sentinel errors.
- `Mode` as a typed string with `Valid()`.
- All JSON tags explicit snake_case. Optional nullable fields use pointer types (e.g., `CapabilitiesUpdate.SessionID *string`); optional-absent fields use `omitempty`.
- `ToolResultRequest` as a type alias of `ToolResult` to reflect shared wire shape without ambiguity.

### Red phase (tester role) — commit `28213eb`

Wrote `protocol_test.go` with:
- Method-name constant assertions (19 types)
- Protocol version check
- `Mode.Valid()` positive and negative cases
- Round-trip tests for every request type, with full and minimal variants for those with optional fields; three variants for `TurnSubmit` (content-only, tool-results-only, full)
- Envelope round-trips (request, success response, error response)
- Framing: round-trip, oversize rejection, embedded-newline rejection, EOF between frames, partial-frame invalid
- `TestCanonicalFieldNames` — snake_case presence + CamelCase negative leak

Stubs in `protocol.go` / `messages.go` left ProtocolVersion empty, MaxFrameSize zero, method constants empty, `Mode.Valid()` always false, JSON tags absent, and framing helpers returning `errNotImplemented`. Tests compiled and failed on every expected axis — proper red phase.

### Green phase (backend role) — commit `1aa3830`

Filled in:
- `ProtocolVersion = "1"`, `MaxFrameSize = 10 * 1024 * 1024`
- Method constants assigned canonical values
- `Mode.Valid()` switch
- `FrameReader.ReadFrame` with bounded buffer, clean EOF between frames, oversize detection
- `FrameWriter.WriteFrame` with embedded-newline rejection
- Complete snake_case JSON tags on all types
- `ToolDefinition.InputSchema` changed from `[]byte` (base64-encoded by default) to `json.RawMessage` (passthrough)

All WU-039 tests pass. `go vet` clean. `gofmt` clean. Full repo build green.

Pre-existing flake in `internal/integration TestMetricsAggregation` (SQLite SQLITE_BUSY under `-race`) confirmed unrelated — reproduces on parent commit.

### Security review (security role) — commit `50febd0`

Log: `.sdlc/history/2026-04-16-security-wu-039-protocol-core.md`

One finding fixed in-session:

- **SR-039-01 (Medium)** — `FrameReader.ReadFrame` called a `drainUntilNewline` helper after detecting an oversize frame. Attacker withholds the newline → drain loops reading arbitrary bytes, defeating `MaxFrameSize`. **Fix:** removed the drain; `ReadFrame` now returns `ErrFrameTooLarge` immediately. Caller must close the connection. Follow-up captured in WU-046 DoD.

Four informational findings documented for later WUs:
- **SR-039-02** → WU-094 (content-type-aware redaction on user-controlled Raw/ConfigContent fields)
- **SR-039-03** → WU-093 (strict decoding via conformance fixtures)
- **SR-039-04** → WU-063, WU-094 (constrain `ErrorObject.Data` to documented diagnostic shapes)
- **SR-039-05** → WU-049, WU-094 (size-cap and validate `ToolDefinition.InputSchema`)
