### Step 1 — provider key resolution (fixed)

**Symptom.** `Error: loading config: provider "anthropic" api_key:
secret: env:ANTHROPIC_API_KEY is empty or unset`.

**Root cause.** The dotenv loader (PATCH-0007,
`internal/dotenv/dotenv.go`) searches three paths and only three:

1. `./.env` — relative to the shell's CWD (so `<repo>/.tmp/.env` here)
2. `$XDG_CONFIG_HOME/modeltap/.env` (if `XDG_CONFIG_HOME` is set)
3. `~/.modeltap/.env`

The user had real keys in `<repo>/.modeltap/.env` — a path the loader
**does not** search. The loader was loading `~/.modeltap/.env`, which
contained the variable names but with empty values (a stale template
from initial setup), so `ANTHROPIC_API_KEY=""` ended up in the process
env and the secret resolver at `internal/config/config.go:292`
correctly rejected the empty value.

**Fix applied.** User copied real values into `~/.modeltap/.env` (or
moved them to `<repo>/.tmp/.env`). Step 1 then passed.

**UX gap noted (not fixed).** Putting `.env` inside a `.modeltap/`
project-local directory is a reasonable expectation that mirrors the
user-level `~/.modeltap/` shape. The loader doesn't honor it. Worth a
future patch to add `./.modeltap/.env` to the search order — not
blocking, but the trap is real.

### Step 2 — `/models` returns empty (open)

**Symptom.** `/models` displays "No models available" in the Bubble Tea
shell.

**What was confirmed by code reading.**

- The `/models` UI command sends `model.list` to the BFF
  (`internal/harnesshost/production_runtime.go:465`).
- The BFF handler returns `srv.models.All()`
  (`internal/bff/routing.go:127`).
- The harness prints "No models available" only when the response's
  `Models` slice is empty
  (`internal/harnesshost/production_runtime.go:474`).
- The BFF's `ModelRegistry` ships built-in catalogs for Anthropic
  (`claude-opus-4-6`, `claude-sonnet-4-6`, `claude-haiku-4-5`) and
  OpenAI (`gpt-5`, etc.) at `internal/bff/registry.go:220+`. Built-ins
  are added in Pass 1 of `rebuildLocked` for every provider type that
  has at least one endpoint configured.
- CLI wiring at `internal/cli/bff_wiring.go:88–101` creates endpoints
  from config and calls `srv.Models().Refresh()` after registration.

**Conclusion.** The BFF is reachable (the call succeeds) but is
genuinely returning zero models. Something in the registration or
config path is wrong at runtime in a way the static code reading
didn't reveal.

### Diagnostic suspects (in order of likelihood)

1. **Stale BFF daemon on the socket.** `bff.socket_path:
   ~/.modeltap/server.sock`. If a previous build of `modeltap serve`
   is still running (or a stale `.sock` is being auto-discovered), the
   harness connects to *that* BFF, which has its own stale provider
   registry from whenever it last started. The shell's "connects to
   the local BFF" message at step 1 doesn't disambiguate fresh vs.
   stale daemon.

   **Quick check:** `lsof ~/.modeltap/server.sock` and `pgrep -af modeltap`.
   If anything is using the socket, kill it and re-run.

2. **Config not being read from the expected path.** If the binary's
   config search path doesn't land on `~/.modeltap/config.yaml`, the
   providers section never reaches the wiring. Possible causes:
   `--config` flag override, `MODELTAP_CONFIG_FILE` env var, or
   working-directory-relative config search.

   **Quick check:** Run `./bin/modeltap config print` (if such a
   command exists) or grep for config-load code paths to confirm
   which file is read.

3. **Endpoint registration silently failing.** `bff_wiring.go:96`
   writes `"BFF provider %q: %v"` to stderr when `Add` errors. In TUI
   mode that stderr line is easy to miss. Possible causes: duplicate
   endpoint name, validation rejection.

   **Quick check:** Launch the shell with stderr captured to a file:
   `./bin/modeltap shell --project "$(pwd)" 2>/tmp/bff.err`
   and inspect after.

4. **API key still empty at wiring time.** The config-load step
   resolves `env:ANTHROPIC_API_KEY` once (and now succeeds with the
   fixed `.env`). But if the binary forks/re-execs or re-loads config
   in a child process and that process didn't get the env var, the
   wiring sees `pc.APIKey == ""` and the endpoint health check sets
   the provider to unavailable. Models would still appear in the list
   under that condition (just marked unavailable), so this is **less
   likely** the cause of an empty list — but worth checking.

   **Quick check:** Add a temporary log in `bff_wiring.go` after the
   `Add` loop to print `endpointCount` and `srv.Models().All()`.

## Follow-up clarification logged

After the smoke-test instructions were written, the user asked whether
`--project` should point at a temp directory and where the "real project
context" lives.

Clarification provided:

- For an isolated smoke test, `--project` can point at a temp/scratch
  directory.
- To associate the smoke run with the actual repository, pass the repo
  root: `./bin/modeltap shell --project /Users/jasonhenderson/Projects/jasonahenderson/modeltap`.
- In the current production shell, `--project` only sets
  `protocol.ProjectContext.Root`.
- v0.3.0 production shell does **not** currently read `.modeltap/`,
  `.modeltap.yaml`, `MODELTAP.md`, `AGENTS.md`, or `CLAUDE.md` into
  `ProjectContext.ConfigContent`.
- Project-rule discovery is planned for later v0.3.x work, mainly
  v0.3.1.
- Global modeltap config/data lives under `~/.modeltap/`; that is not
  the per-project context directory.
